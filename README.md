# AInki

A personal Russian learning system with two halves:
- **IN**: SM-2 vocabulary review
- **OUT**: LLM-driven grammar evaluation

## Problem: Output

After four years of Russian study I have strong listening comprehension —
solid C1, comfortable with native anime, TV, and podcasts — but weak
productive grammar. I have read extensively in Russian, including books with
C2+ vocabulary, so comprehension is not the bottleneck. Textbooks, lessons
with teachers, and standard LLM interfaces all failed to move me past that
ceiling, because none of them drilled grammar rules to automaticity or
tracked progress at the level of specific lexical-grammatical patterns.

## Problem: Input

I had been using Anki with sentence mining for over a year. The overall
workflow was highly inefficient and mentally taxing. After a year I had
accumulated thousands of sentence cards with useless antiquated vocabulary
from books and articles, and I felt I could build a better system using
DeepSeek.

## What this project demonstrates

I built AInki to solve my own bottleneck, then built the infrastructure to
evaluate it honestly. The project demonstrates:

- **A multi-stage LLM pipeline** where each call has a distinct role
  (generation, verification, grading) and each stage has explicit failure
  handling. The system does not trust a single model output.
- **Structured rubric design** that separates form-errors from orthographic
  errors, so inaudible spelling mistakes (`-тся` vs. `-ться`, `-ый` vs. `-ий`)
  do not contaminate the grammar-accuracy signal.
- **Facet-level tracking granularity** — rather than scoring a rule as
  "passed" or "failed," the system tracks 300+ specific lexical-grammatical
  facets within rules. Mastery requires 3+ consecutive clean drills across
  *all* facets of a rule, not just any one.
- **State consistency under real usage** — pause-aware scheduling, epoch
  counters for buffer invalidation, atomic writes on every verdict, an undo
  stack that survives session boundaries, and a daily freeze so a page
  refresh does not re-consume new cards.
- **Evaluation-first design** — the system's whole point is measurable
  improvement in productive grammar, not looking busy. Every decision was
  made against that criterion.

## Solution: Output

A three-state model per grammar rule (unlearned → learning → mastered), with
per-facet tracking of 300+ specific items. Drills are generated by an LLM,
verified by a second call, and graded by a third. Only the target rule's
state updates.

## Solution: Input

An AI-powered sentence generator drawn from a manually sorted frequency list
combining new words I want to learn with known words I want to practice.
The frequency list contains roughly 20,000 Russian words, manually sorted
into three buckets: ~3,000 words I still need to learn, ~10,000 words I want
to practice for active production, and ~7,000 words I've mastered or don't
want to learn. Sentences also draw from a list of core grammatical
constructions — *тем не менее*, *как будто бы*, and so on — also manually
sorted based on which ones I don't know or know but want to practice. By
default, ten new sentences are added per day, each containing one new word,
one to three practice words, and one new or practice grammatical
construction. The SM-2 algorithm handles SRS rating and scheduling.

## Key design decisions: Output

### SRS vs. state model
Words are forgettable — SRS fits. Grammar rules are few and interdependent —
a state model fits better.

### Facet tracking
"Drill R022" doesn't mean anything; R022 is 50 verbs. Per-item tracking
ensures the system covers the whole family.

### Typo vs. grammar distinction
Inaudible spelling variants (`-ый` vs. `-ий`, `-тся` vs. `-ться`) are not
grammar errors. The rubric distinguishes form-errors from orthographic
errors. I made this decision after watching my own accuracy numbers degrade
on inaudible mistakes — the state file was measuring my keyboard habits, not
my grammar.

### Target-rule-only verdict
A drill on dative with a prepositional phrase shouldn't fail on the
prepositional error. The verdict classifies only the target rule. Without
this, a single weak rule poisons every drill that touches it and progress
becomes unmeasurable.

### Race condition handling
Drills generated for one topic landing after the topic changes were buffered.
Fixed with an epoch counter.

## Key design decisions: Input

### SM-2 over a custom scheduler
The card scheduler is standard SM-2 with learning steps — not a custom or
proprietary model. SM-2 is stable, well-documented, and sufficient for a
deck that starts small and grows to a few thousand cards. I identified the
FSRS upgrade path (seed FSRS state from the existing ease/interval) but it
isn't the current bottleneck.

### Learning steps separate from review scheduling
New cards pass through 1/10/30-minute learning steps before graduating to
a 1-day review interval. This mirrors Anki's behavior and keeps the "when do
I see this word again" decision decoupled from the "how well do I know it"
decision. The SRS engine tracks both independently.

### Within-session spacing is a frontend concern
The engine returns learning cards unconditionally — it ignores their
`due_date` and hands them to the client, which parks cards that aren't ready
yet in a pending queue. If the queue empties before the pending cards'
intervals elapse, the soonest one is force-promoted. This gives the "wait
the real interval, but don't end a session with learning cards pending"
behavior without the engine having to know about session state.

### Daily cap on new cards
`new_cards_per_day` is a hard cap, not a soft target. Once the cap is hit,
no more new cards are served until the next calendar day. Introduced cards
are marked with an `introduced_date` so the same batch isn't re-served on
refresh or server restart.

### Pause tracking shifts the whole schedule
When days are skipped, the daily generator pushes every card's
`last_reviewed` and `due_date` forward by the number of missed days. The
system resumes as if no time passed — no backlog, no avalanche. The shift
is only applied when the generator next runs, so skip detection is tied to
actual usage rather than wall-clock time.

## Key design decisions: Interface

### Full-viewport shell, two halves in one page
The app is a single-page shell with a header (mode toggle, language toggle,
session state) and two halves — IN (SRS) and OUT (grammar) — that swap
visibility based on the header toggle. State persists in localStorage.
Splitting into separate pages would have broken the "Tab to swap between
panes" interaction, which depends on both halves living in the same document.

### Tab swaps focus between the top and bottom pane
In both halves, Tab moves focus between the primary content pane and the
chat pane. Each pane remembers its last-focused element, so returning to a
pane restores the cursor. The design assumes the mouse is used only for the
initial folder pick, not for regular use.

### Keyboard-first, with mouse as fallback
Every action has a keyboard binding. IN: arrow keys / WASD for ratings,
Shift for pause, Backspace for undo, S for TTS. OUT: Enter to submit, Up to
focus the prompt line, Left/Right/Shift for word selection. Buttons exist
for discoverability but are not required. Reducing friction was the whole
point — if rating a card takes more than a thumb press, the system is
failing.

### One chat pane per half, sharing the same LLM
Both halves have a chat pane below the primary content. Shortcuts work the
same way in both (`e` = explain word, `.` = explain sentence, `?` = explain
context). Chat history persists per session and resets on new generation. A
single shared chat would have muddied the context: a question about the
current drill shouldn't leak into a question about the current card.

### Language toggle affects LLM output, not input
The EN/RU toggle changes what language the LLM replies in (drill critiques,
write prompts, chat responses). It does not change what language the user
types in. The write pane is always Russian; the chat is always English.
This keeps keyboard layout switching out of the session.

### Structured feedback, not prose
Grading returns a fixed format: verdict line, correction count, corrections
grouped by grammar category, full corrected sentence. The format is enforced
in the prompt and validated on the way in. Verdicts need to be parseable
into state updates; corrections need to be scannable; the structure forces
the model to commit to specific claims rather than hedge with general
commentary.

### Visual pacing without numeric pressure
The session timer and card timer use a colored sweep inside the progress
bar. Color shifts from cool to warm as time elapses. No numbers, no
countdowns, no failure state — the sweep meeting the progress bar edge is
the only "you're late" signal. Numeric timers on language learning apps
create anxiety that degrades retention. A visual metronome keeps pace
without triggering stress.

## Open problems and roadmap

Three areas where I know the current system is weak and have concrete plans
to fix them:

**Drill history and content spacing.** The system currently tracks rule
coverage but not content coverage. The drill generator can produce
near-identical sentences across multiple days — for example, repeatedly
testing dative with variations on "The teacher gave the students lots of
pencils and notebooks for the lesson." A rule can reach "mastered" state
while I've only practiced one sentence pattern. My plan is to fingerprint
each generated drill (sentence template plus a set of key content words)
and apply SM-2-style spacing to the fingerprints themselves, so the
generator is forced to produce structurally and lexically distinct drills.
Templates that were just used are unavailable for N days; lexical chunks
that were just tested get pushed back; the generator receives the last N
fingerprints as a blacklist in its prompt.

**Bridging the two halves.** IN and OUT are currently independent: IN
trains passive recognition, OUT trains productive grammar, but they don't
share vocabulary. The long-term design is that once a grammar rule is
mastered, its drills start seeding vocabulary from the IN sentence
generator — pulling words that are "passive but not active" into drill
sentences, and adding a second verdict dimension (target word used
correctly) to grading. Correct production of an IN-origin word in an OUT
drill is what promotes it from passive to active. This is the graduation
from "I can read" to "I can speak."

**Free chat as a graded mode.** Drills test production against a specific
target; write mode tests production against a prompt. Neither tests
production under conversational pressure. I plan to add a mode in the OUT
half where the LLM either issues a prompt ("Describe your morning in 5-8
sentences") or holds a free conversation with me, responding turn by turn.
Everything I write in that mode gets graded through the same rubric as
drills — corrections tagged against the same rules and facets, verdicts
feeding into the same state file, identical correction output. The mode
addition is about elicitation style (constrained prompt vs. free
conversation), not about the grading system, which is already built and
proven.

## Companion project: Chinanki

I built a second system in parallel, Chinanki, a daily Mandarin reading app
that applies the same philosophy to a language with different structural
constraints. Chinanki generates a short Chinese story each day under a hard
vocabulary constraint — only words already known may appear, plus a small
batch of new words and the words due for SRS review — then renders it in a
custom reader with word-level pinyin, click-to-reveal glosses, and audio.
It is the same underlying idea as AInki's IN half, adapted to Mandarin:
comprehensible input delivered at a controlled difficulty, with the reader
as the delivery vehicle and SRS as the engine.

The two projects together demonstrate a specific design stance: language
acquisition happens when a system produces content at the right difficulty
for the learner, day after day, and quietly measures whether it's working.
Both projects are self-contained, both use DeepSeek for generation, 
both ship as static frontends served by Python stdlib HTTP, and both were
built solo.

## Running it

1. Install Python 3.9+, Flask, requests
2. Copy `data-template/` to `data/`
3. Copy `config/config.template.json` to `config/config.json` and set `DEEPSEEK_API_KEY` in `.env`
4. Run `python3 src/server.py`
5. Open `http://127.0.0.1:5000`

## What I learned

- SRS is the right model for vocabulary, not grammar.
- LLM output can't be trusted without verification.
- Tracking granularity determines signal quality.
- Inaudible errors corrupt metrics if not distinguished.
- A system that measures itself honestly is worth more than one that just
  looks busy.
